OCUDUAgentBench — Technical Reference

The deep technical doc behind the benchmark/ harness. Covers the whole project: task contract, benchmark surface, simulated runtime adapter, episode lifecycle, trace partitions, scoring, the real-LLM agent harness, and the invariants that hold across all of it.

1. Overview

OCUDUAgentBench evaluates LLM agents that operate an OCUDU 5G stack over ZeroMQ. Every task is one scored episode: the benchmark drives a deterministic stimulus schedule against a runtime adapter, the agent reads redacted observations and emits actions, and an oracle scores the recorded trace after the run. This doc is the implementation reference — it assumes you have already read the README for positioning and quick-start, and the design records under skillful-ran-research/benchmark_design/ for the why.

Reading order is top-down: terminology → system layers → task contract → agent surface → benchmark surface → simulated runtime → episode lifecycle and the per-step swimlane → trace partitions → scoring → real-LLM integration → operations → invariants. The architecture sits in §3; the per-step pipeline in §7; the scoring pipeline in §9.

3. System architecture — five layers + one future surface

The harness is a strict-layered Python system. The top layer is what the LLM sees; the bottom layer is the only place that mutates runtime state. The colored layers form the per-episode call path; the dashed bottom layer reserves space for a future live adapter that the current code does not claim to drive. Every block is implemented in benchmark/benchmark_api/ or benchmark/agents/.

4. The task contract T = ⟨G, E, U, I, J⟩ + M

Every task is loaded as a PrivateTask with five contract fields plus a private metadata bag. The contract is the single source of truth for what the agent sees, what the runtime does, and how the run is scored.

FieldOwnerVisibilityMeaning
Gtask manifestagent-visibleGoal text. Public after generated-axis redaction.
Eruntime setupbenchmark-privateRuntime adapter, components, site config. All current tasks declare E.runtime_adapter = simulated_ocudu.
Ustimulus planbenchmark-privateDeterministic, step-targeted runtime dynamics. Seed-controlled.
IAPI projectionpartly visibleAllowed action APIs, observation sources, observation-detail mode (repair_targets vs diagnosis_symptoms), and allow_no_action.
Joracle scoringprivate during runRaw metrics, critical metrics, temporal expectations, expected action fields, expected post-action evidence.
Mcatalog/generatorbenchmark-privatetask_set, family, role; generated tasks add variant with axis, level, anchor, seed, registry/policy SHA-256s. Never serialized to agent observations or feedback.

Two derived projections drop out of the contract — both built by task_definition.py:

  • AgentVisibleTask — G, the API projection filtered to I.allowed_actions, the observation/action/feedback schema paths, I.public_constraints. Everything else is dropped.
  • task_provenance(...) — built per run: task-definition SHA-256, suite seed/count, family filter, source path, and generated registry/policy checksums. Copied into the scored summary for replay.

5. Agent surface — what the LLM sees

The agent surface is intentionally narrow. The agent receives only the redacted task view at session start, then one observation per step. It returns one decision per step (an action object or null for no-action). Each decision is followed by a redacted feedback record.

Observation frame

Constructed by observation.py:

  • step_id, observation_timestamp_s, task_id
  • evidence — filtered by I.observation_sources and I.observation_detail; private field names (E, U, J, seed, runtime_handle, oracle, artifact_path, setup_metadata, stimulus_schedule, future_stimulus) trigger a hard error if they appear anywhere in the frame
  • previous_feedback — the last redacted feedback record, or null on step 1
  • context — subset of (task_id, step_id, backend) limited by allowed_observation_context

Observation-detail modes

ModeExposesHides
repair_targets Direct repair fields: target_prb_policy, target_ssb_block_power_dbm, target_cfo_hz, target_tx_time_offset_us, mismatch desired registration. Private stimulus parameters, oracle requirements.
diagnosis_symptoms Public symptoms only: SINR, CQI, RSRP, RSRQ, queue pressure, PRB utilization, backhaul delay/loss, redacted core/registration state. All direct repair targets (the agent must infer them) plus the private fields above.

Action validation

The agent submits one decision per step. action.py validates and normalizes it before dispatch:

  1. null → NO_ACTION (allowed only when I.allow_no_action is true)
  2. Non-dict → schema_error
  3. Unknown type, or type not in I.allowed_actions → permission_error
  4. Per-action field validators enforce ranges — PRB ratios ∈ [0, 100], min ≤ max; PCI ∈ [0, 1007]; CFO ∈ [-100 000, 100 000] Hz; SUPI is 5–16 digits; RNTI is a non-zero 16-bit integer or hex string

Validated actions go to dispatch_runtime_action(), then to simulated_ocudu.py (§6). The result becomes a redacted feedback record with status, action_outcome.accepted, optional safe_error_class, and a human-readable safe_message. The redacted feedback is the only signal the agent sees about acceptance.

6. Benchmark surface — task sets, variants, stimulus, runtime

Task sets

Tasks live under benchmark/task_sets/. Suite resolution is owned by task_catalog.py:

Generated variants

Generated suites scale coverage without committing hundreds of task directories. The model is:

anchor task  +  variant axis/vector  +  suite seed  =  in-memory PrivateTask
  • task_sets/generated/axis_registry.json — for each anchor, defines axes (levels[] or sampler.transform), expected failure modes, and manifest overrides.
  • task_sets/generated/suite_policies.json — default counts, balancing policy (family + expected_failure_modes), interaction depth, exhaustion behavior.
  • Nine sampler transforms cover PRB ratio, SSB power, CFO target, TX offset, handover identity, CHO targets, core NF target, core UE mismatch, and no-action symptoms.
  • Public ID format is generated_sNNNN_hash_v1 — opaque on purpose. Axis name, anchor task ID, sampled values, and expected failure modes stay in private M.variant; registry and policy SHA-256s are recorded in run provenance for replay.

Stimulus scheduling

U is expanded to a concrete plan by expand_stimulus_plan(U, seed) before the scored interaction starts. The plan never adapts to the agent's actions — it is a fixed schedule.

ConceptMechanism
Step targetingapply_steps: [...] for explicit step IDs, or start_step+end_step for a closed range. Mutually exclusive. Omitting both targets every step.
Phasespre_observation events apply before the observation is built; in_step events become active when the observation is emitted and end at the step boundary (after the agent's action completes or the step deadline elapses).
Timing policyclock_mode ∈ {fixed_tick, virtual_clock, wall_clock}; step_interval_s ≥ decision_deadline_s (enforced); late agent decisions fall through to NO_ACTION.
Implemented drivers16 kinds in StimulusDriverKind: traffic load, UE churn, mobility path, radio condition, slice demand shift, telemetry gap, E2 KPM window, RIC xApp lifecycle, core latency / UE registration, backhaul impairment, cell identity change, future ZMQ impairment, plus the two infrastructure drivers (docker_zmq_runtime_launch, metrics_staleness_mask).

The simulated_ocudu runtime adapter

simulated_ocudu is the only adapter currently wired to the dispatcher. It is an executable benchmark adapter, not a live OCUDU/FlexRIC connection. It closes the loop so that accepted actions visibly change later evidence — which is what makes expected_post_action_evidence a meaningful score signal.

Action familySimulated effectRepresentative rejection
PRB policy (WS / CCC / RC_DU)Updates slice_runtime.current_prb_policy and later slice evidence.Wrong slice identifiers; E2 backend without available KPM evidence; duplicate policy already applied.
SSB powerUpdates radio_runtime.current_ssb_block_power_dbm, tags the responsible cell.Stale or wrong cell identity; duplicate power already applied.
HO / CHOMoves UE serving PCI or records a conditional handover plan.Wrong RNTI, wrong serving PCI, or target outside the candidate set.
CFO / TX offsetUpdates radio impairment state and sets a correction flag if the target matches.Wrong sector or duplicate correction.
Core NF restartUpdates NF status, restart counts, degradation state.NF not in available_nfs; repeated restart after recovery.
Core UE registrationUpdates registration to the desired profile.Payload does not match the desired benchmark profile; duplicate update after registered.

All rejections produce safe_error_class = runtime_rejected with a public message and append to control_outcomes. The agent learns the safe class and message; the private cause stays in the benchmark trace.

Why a simulated adapter is the default. The closed-loop simulator makes the harness self-checking: deterministic stimulus, deterministic transitions, and observable post-action evidence let scoring detect not only what action the agent took but whether it actually moved the runtime. A live adapter would replace this layer but keep the same task contract, redaction, and scoring.

7. Episode lifecycle — owners, ordering, the per-step pipeline

episode.py owns one scored run. Scoring is post-run by design: the agent never sees scores during the interaction.

The run is a strict pipeline: load → project → instantiate → expand → readiness → interact → finalize → score. Each later stage assumes the guarantee the previous one made. The per-step interaction (step 6 expanded) is where the four resources — agent, episode orchestrator, benchmark logic, runtime adapter — hand off in sequence. The shape, laid out by resource, reads like this:

Per-step detail

  1. Apply pre_observation stimulus events to the runtime; record each to the private partition.
  2. Build the observation frame (filtered evidence + redacted previous feedback); record it.
  3. Start any in_step stimulus at the observation timestamp.
  4. The wrapper requests an agent decision under decision_deadline_s; timeout or malformed result becomes NO_ACTION.
  5. action.py validates and normalizes the decision (or rejects with a safe_error_class).
  6. dispatch_runtime_action → simulated_ocudu (skipped for NO_ACTION).
  7. Finish in_step stimulus at the step boundary; build and record redacted feedback; carry it forward as previous_feedback.

Finalization ordering

This ordering is invariant — scoring.score_episode rejects any package that violates it:

  1. Finalize artifact manifest (trace.finalize_artifacts).
  2. Cleanup runtime; record cleanup oracle entry.
  3. Finalize trace (checksum and persist).
  4. Score the finalized package; persist the scored summary.

9. Scoring pipeline

Scoring is implemented in scoring.py and runs once, on the finalized trace. It is deliberately deterministic and uniform across tasks: every task uses the same pipeline; only its requested raw_metrics and critical_metrics differ.

Critical raw metrics

The metrics that decide pass/fail when included in J.critical_metrics:

  • temporal_action_sequence_match — actions at the right step IDs with the right validity/acceptance.
  • expected_action_payload_match — payload fields match (numeric tolerance from J).
  • post_action_evidence_match — later observation reflects the action's runtime effect.
  • valid_action_accepted_rate, action_budget_ok, expected_action_type_correct, noop_correctness, unnecessary_action_avoidance, evidence_gated_action, stale_action_avoidance — safety and evidence-use gates.
  • Domain-specific: cli_cfo_target_match, cli_tx_time_offset_target_match, core_ue_registration_repaired.

Diagnostic similarity metrics

action_timing_similarity, expected_action_payload_similarity, and post_action_evidence_similarity give graded resolution between full pass and full fail. Always requested for generated tasks; never gate the outcome.

Component scores

ComponentAveraged raw metrics
task_correctnessexpected action type · triage · temporal sequence · payload match · post-action evidence · noop correctness
action_correctnessvalid-accepted rate · correct API · repair success · domain matches
evidence_useevidence-gated · stale-action avoidance · temporal sequence
ran_healthping ratio · metrics continuity · E2 KPM continuity

Efficiency — decoupled

Recorded separately and never affecting correctness: task completion time; decision-latency mean / p50 / p95; control round-trip mean / p50 / p95; prompt / completion / reasoning / total tokens; tokens-per-decision mean; tokens-to-task-success.

10. Real-LLM agent integration

The benchmark's agent contract is a plain Callable[[dict], dict]. The package benchmark/agents/ implements one such callable (LLMAgent) that issues exactly one chat completion per step, plus a runner that clones the selected task with a relaxed timing policy so LLM-scale latency fits inside the per-step budget. The benchmark core under benchmark/benchmark_api/ is unchanged.

Backend deployment modes

ModeBackendTypical use
A — self-hostedOpenAICompatibleBackend at any base URLLocal Ollama / vLLM / llama.cpp / LM Studio / TabbyAPI on a workstation, optionally over a LAN tunnel
B — commercial APIsame plus AnthropicBackend for native MessagesOpenAI, Anthropic, OpenRouter, Together, Groq, Fireworks, Mistral, DeepSeek
offlineEchoBackendUnit tests (10 included) and offline smoke checks without network

All three implement the LLMBackend protocol with one method complete(messages) → LLMResponse. The runner uses stdlib urllib.request + json only — no new dependencies.

Why a separate runner

Checked-in task manifests set U.timing_policy.decision_deadline_s = 0.01 s for the deterministic baselines (which respond in microseconds). Any real LLM call is orders of magnitude slower, so runner.relax_task_clock clones the selected task with step_interval_s = decision_deadline_s + padding before scoring. The benchmark core does not need any changes; the wrapper still enforces the deadline — if the LLM call exceeds it, the step is automatically converted to NO_ACTION and tagged telemetry.timed_out = True.

One step in detail

For every step agent_api_wrapper.py calls LLMAgent(payload); the agent does:

  1. build_messages(payload) — system message (role + JSON-only output requirement + per-task action cheatsheet from action_schemas.py); user message (goal, public constraints, observation, previous feedback, decision timeout).
  2. backend.complete(messages) — one HTTP round-trip to the provider.
  3. parse_decision(text) — accepts bare JSON, fenced JSON code blocks, the literal null, or the {type: NO_ACTION} shorthand. Anything else returns NO_ACTION with a descriptive parse_status.
  4. Returns {decision, telemetry} with token usage, decision latency, model, provider, parse status, and optional rationale (capped at 400 chars).

Backend transport errors (HTTP 4xx/5xx, network errors) degrade to NO_ACTION with telemetry.parse_status = "transport_error" and a 400-char excerpt of the underlying error. The episode continues to completion and scoring sees the failure as NO_ACTION instead of crashing.

Failure modes captured in telemetry

parse_statusTrigger
okmodel emitted parseable JSON with a top-level decision field
emptybackend returned an empty body
no_jsonresponse had no {...} or literal null
invalid_jsoncandidate substring failed json.loads
unrecognized_shapeJSON parsed but had no decision or type key

python3 benchmark/benchctl.py --json run --suite all_checked_in --controller auto
python3 benchmark/benchctl.py --json run --suite standard --controller auto --seed 1 --count 200
python3 benchmark/benchctl.py --json remote check --config .config
python3 benchmark/benchctl.py --json remote sync --config .config --dry-run
  • episode run — one episode; with --output-dir writes <run_id>.trace.json and <run_id>.summary.json after finalization.
  • run — repeated runs over one task or a whole suite (controller.py); per-run scored summaries are aggregated by suite.py.
  • tasks list — for generated suites, deterministic for (suite, seed, count, family).

Remote workflow boundary

remote sync copies the local benchmark/ tree to <remote.workspace>/synced/benchmark/ with rsync --delete. It is an implementation utility for running the same simulated benchmark on a configured remote workstation. It does not turn a run into a live OCUDU/FlexRIC benchmark — live-runtime claims require a separate adapter with readiness, dispatch, artifact, cleanup, and oracle support. The remote runbook lives at benchmark/remote_validation_runbook.md.

12. Invariants to preserve

Six properties hold across the harness. Changes that break any of them must update the relevant design record under skillful-ran-research/benchmark_design/ before the code merges.

  1. Redaction is positive, not negative. Observations and feedback are built from explicit allow-lists; a leak guard rejects any frame containing private field names. M.variant never enters the agent view.
  2. Allowed actions are anchored to selected APIs. I.allowed_actions ⊆ action types projected from I.api_kinds; manifest validation rejects violators.
  3. Expected payloads must be derivable from public sources. Conformance refuses to start a run whose J.expected_action_fields requires sources missing from I.observation_sources. Same for J.expected_post_action_evidence.
  4. Stimulus is fixed at expansion time. The agent's actions do not change the schedule. Step targeting is validated; only implemented drivers can appear.
  5. Finalize before score. Scoring refuses unfinalized trace packages. The order is: artifacts → cleanup → trace → score.
  6. Simulated runs cannot claim live runtime. simulated_ocudu is documented as such; live adapter work must prove real OCUDU/FlexRIC/UE/core effects before the docs or benchmark widen the claim.

13. Scope and planned work

Scope today

  • Deterministic baselines (auto, noop, fixed_prb, …) operate the full checked-in surface end-to-end.
  • Real-LLM agents operate the full surface through one of the supported backends; first scored episode end-to-end has been demonstrated on a self-hosted vLLM instance with a small Qwen 2.5 model.
  • Runtime adapter is simulated_ocudu only. Not yet wired: live OCUDU/FlexRIC.
  • Comparison sweep (N models × M tasks) is not yet a single command; today it's an external loop around agents/runner.py.

Planned work

  • benchmark/agents/sweep.py — model × task matrix runner that writes a consolidated sweep_summary.json.
  • Backend retry / exponential backoff on HTTP 4xx / 5xx and network errors — critical before a commercial-API sweep.
  • Per-model serving config in models.json (e.g. max_tokens for reasoning models, gpu_memory_utilization for concurrent serving).
  • Live OCUDU/FlexRIC adapter — same task contract, redaction, and scoring as simulated_ocudu; replaces only the runtime layer in §3.
