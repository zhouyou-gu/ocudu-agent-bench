Emulated Agent Benchmark Setup And Results

This file records the deterministic no-real-agent benchmark tests under benchmark/tests/emulated_agents/. The tests use simulated_ocudu only; they do not claim live OCUDU, FlexRIC, UE, or core execution.

A current design concern is that these emulated-agent results show coarse performance separation, not yet the full diagnostic resolution expected from a strong RAN-control benchmark. Extracting more fields from traces can help explain failures, but it has limited effect if the tasks themselves do not isolate one narrow skill difference at a time. Higher-resolution evaluation should come mainly from carefully designed contrast tasks that zoom in on timing, evidence gating, API choice, payload precision, repair behavior, and post-action runtime effects.

Score Definitions

All correctness scores are normalized from 0.0 to 1.0. A run succeeds only when every task-critical raw metric reaches the task threshold, usually 1.0. Component scores summarize behavior for analysis; they do not replace the raw-metric pass/fail rule.

ScoreDefinition
task_correctnessMean of the task-level raw checks present in the manifest: expected action type, no-action correctness, triage success, temporal sequence, expected payload, and post-action evidence.
action_correctnessMean of the action/API checks present in the manifest: accepted valid actions, API selection, repair success, core registration repair, CFO/TX offset target match, expected payload, and post-action evidence.
evidence_useMean of evidence-gating checks: action after required evidence, stale-metrics restraint, and expected timing sequence.
ran_healthMean of observed runtime-health checks when requested: ping success, metrics continuity, and E2 KPM continuity.
safetyMean of safety/restraint checks: action budget, unnecessary-action avoidance, and invalid-action rejection where applicable.
efficiencyLatency, control round-trip, and token telemetry. These fields explain cost and speed but do not change correctness.

Interpretation

The good profile passes the full 34-task checked-in matrix and deterministic generated samples. Bad profiles fail for distinct reasons: no action, early action, late action, wrong API family, wrong payload, repeated control after repair, or unsafe control when no RAN action is warranted.

The closed-loop simulator changes make payload-correctness and runtime-effect correctness separable: an accepted action must now leave the expected public state in the later observation, not only match the command schema.
